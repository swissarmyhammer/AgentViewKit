title: Find why a scroll to the bottom in AgentThreadView can stop two rows above the last row in the hosted harness
---
Source: the implement step of ^sh4msc4 (the hang of the full `swift test` run).

Discovery: in `ThreadFloatingControlsHostedTests`, after a press on the scroll-to-bottom pill of `AgentThreadView`, the result of the scroll to the bottom is not always the same in the off-screen harness window:
- When an update of SwiftUI applies the scroll (the test waits for the bottom scroll target, and SwiftUI updates first), the list goes to the last row (`agent-message-conversation-m29`).
- When a `HostedViewHarness.render()` pass of the test applies the scroll (the test calls `anchors.onScroll(.bottom)` and then `render()`, or the test resumes before the update of SwiftUI), the list stops at `agent-message-conversation-m27`, two rows above the last row. More render passes, `CATransaction.flush()`, `layoutIfNeeded()` and `display()` do not move it. The manager stays pinned (it waits for the report of the bottom rows), so the pill does not show.
- One run gave an empty report of the rows in view after one render pass.
- In `ConversationView` alone (`ConversationViewHostedTests.aPressOnThePillScrollsTheListToTheLastRow`), the same scroll in a render pass goes to the last row. Thus the difference is in `AgentThreadView`, possibly the `.safeAreaBar(edge: .bottom)` of the floating controls, whose height changes when the pill goes away.

Do:
- Find the cause. Tell if a user can see the same stop in the app (the list pinned, two rows above the last row, with no pill).
- If it is a product defect, correct it with a test first.
- Then give `ThreadFloatingControlsHostedTests.aPressOnThePillOfTheThreadRequestsTheScrollToTheBottom` a certain check that the list of the thread moves to the last row. The check must not wait for a report that only a layout pass of SwiftUI can write (no event wait that is not certain, no retry, sleep, poll, clock or time limit). #avk-8
