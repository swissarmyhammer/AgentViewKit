    ### implement — stuck (root cause found in swift-build; no AVK-side fix)

    **Repro**: `swift build --target Cmlx` in wt/mlx-warning (Swift 6.4, swiftlang-6.4.0.34.1) prints
    `warning: missing creator for mutated node: ('<.build>/out/Products/Debug/mlx-swift_Cmlx.bundle/Contents/MacOS')`.
    A 1-target scratch package with one `add.metal` file gets the same warning for `Repro_Shaders.bundle/Contents/MacOS`. The same package with a `.process("data.txt")` resource and no .metal is clean. So any SwiftPM target with .metal sources triggers it. mlx-swift has no bug of its own here.

    **Chain (evidence from .build/manifest.pif and XCBuildData/manifest.json)**
    1. SwiftPM `Sources/SwiftBuildSupport/PackagePIFProjectBuilder.swift` (release/6.4.0):
       - Gives the resource target `mlx-swift_Cmlx` the product type `com.apple.product-type.bundle` and sets `EXECUTABLE_NAME = ""`.
       - Puts `.process` Metal files into that bundle target's **sources** phase ("Metal source code needs to be added to the source build phase"). The PIF shows 10 .metal build files in `PACKAGE-RESOURCE:Cmlx::BUILDPHASE_0` (sources) and no resources phase.
    2. swift-build `Sources/SWBTaskConstruction/TaskProducers/TaskProducer.swift` `willProduceBinary(_:forArch:)`:
       - Treats any sources-phase file as object-producing. Only `sourcecode.applescript` is excluded.
       - So it returns true for a bundle whose only sources are .metal. Those compile to .air → default.metallib, never to a Mach-O.
    3. swift-build `Sources/SWBCore/SpecImplementations/Tools/CodeSign.swift` `constructCodesignTasks`:
       - With `isProducingBinary` true and a BundleProductTypeSpec, it sets `binaryPath = TARGET_BUILD_DIR/EXECUTABLE_PATH`, which is `mlx-swift_Cmlx.bundle/Contents/MacOS/` because the name is empty.
       - It adds that path as both input and output.
    4. swift-build `Sources/SWBTaskExecution/BuildDescription.swift`:
       - A node that is both input and output of one task is "mutated", so the manifest node gets `is-mutated: true`.
       - No Ld task produces it, so the `guard let creator = info.creator` branch emits the warning.
       - The on-disk bundle has only Info.plist, Resources/default.metallib and _CodeSignature. There is no MacOS directory.
    - swift-build main (df26ac2, 2026-10-29) has the same `willProduceBinary` and CodeSign code, so it is unfixed. `gh search issues` finds no existing report in swift-build, swift-package-manager or mlx-swift.

    **Why AVK can't fix it**
    - MLX is needed (see the earlier comment).
    - Every mlx-swift version ships Cmlx .metal sources.
    - AVK can't set build settings on a dependency's synthesized resource target.
    - `--build-system native` doesn't compile .metal, so default.metallib would be lost. That drops functionality and works around the cause instead of fixing it.

    **Proposed upstream fix (swiftlang/swift-build)**: in `willProduceBinary`, exclude Metal sources next to the AppleScript exclusion:
    ```swift
    // Metal files compile to .air/.metallib, never into the linked Mach-O.
    if buildFile.fileType.conformsTo(identifier: "sourcecode.metal") { return false }
    ```
    Belt-and-braces: in `CodeSign.swift`, skip adding the binary node when `EXECUTABLE_NAME` evaluates empty. Add a TaskConstructionTests case: a package resource bundle with only a .metal file must have no mutated `Contents/MacOS` node, using `checkMutatingTasks`.

    **mlx-swift workaround (only if swift-build won't move)**: a build-tool plugin that compiles default.metallib and declares it as a generated resource. That keeps .metal out of the sources phase.

    No commit. wt/mlx-warning is unchanged.
