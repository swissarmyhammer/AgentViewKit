Found by the implement step of ^66has33 (2026-10-23).

Repro (hosted): `Tests/AgentViewKitTests/ACP/ACPWindowReplica.swift` (NavigationSplitView + toolbar, titled window, the in-memory demo agent with its sign-in card) at 1100 by 700, 760 or 820 points. Send "hello". The test process stops with NSGenericException: "The window has been marked as needing another Update Constraints in Window pass, but it has already had more Update Constraints in Window passes than there are views in the window." The stack has `SplitViewChildController hostingView(_:didUpdateMinSize:maxSize:)`.

Probe output (print in ConversationView and ScrollAnchorManager):
- The scroll view of the list is taller than the window (visible height 919 to 1018 points in a 760 point window). The sum of the top and bottom insets stays 660.9 points.
- `position.scrollTo(edge: .bottom)` puts the short content (one user row, 99 points) under the top bar (offset -113.6 with top inset 291.5). The list reports no visible row, and the manager unpins.
- The scroll-to-bottom pill shows in the bottom bar (+32 points). The row is visible again, the manager pins, the pill goes away, and the loop starts again.
- With the `ConversationPill` line removed from `AgentThreadView.floatingControls`, the same size passes.

In the demo app, AppKit catches the exception in the run loop. The AX tree then showed the list content as `Other` 0x0 with no rows, and the state banner stayed at "The agent is working".

The demo now opens at DemoWindowLayout.defaultSize (1100 by 900), so the demo UI test does not get this state. A host window that is smaller than the bars of the thread still gets it.

To do: make the thread layout end in a column that is shorter than its bars. Candidates: a show or a hide of the pill must not change the pin state (the pill height feeds back into the visibility report), and an empty visibility report must not unpin the list. Keep the documented order of the floating controls (banner, sign-in card, pill, composer) or record a decision to change it.
